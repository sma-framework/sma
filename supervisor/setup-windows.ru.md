# SMA V5 — запуск ночного работника на Windows (обвязка Планировщика заданий)

*English version: [`setup-windows.md`](setup-windows.md).*

Это windows-двойник [`setup-macos.ru.md`](setup-macos.ru.md): тот же тонкий слой
супервизора, но под Планировщик заданий Windows вместо launchd. Ядро демона
host-agnostic; здесь только привязка к ОС.

Порядок ниже проверен на референс-машине Windows — без прав администратора, без
docker, без клиента `psql`. Шаги, которые Вы выполняете руками, написаны простым
языком. Инженерные детали идут ниже отдельными блоками.

> **Важно про безопасность.** Задача Планировщика поставляется ВЫКЛЮЧЕННОЙ, и этот
> чек-лист её не регистрирует. Регистрацию и включение выполняет владелец машины,
> вручную, после того как смоук ниже прошёл. Демон никогда не обращается к origin:
> у него нет пути к глаголу публикации. Одобренная работа возвращается обратным
> путём — владелец добавляет этот ПК как git-remote и забирает локальную ветку сам.

## 1. Что нужно заранее (prerequisites)

- **Node.js 22.5 или новее** и **git** в PATH. Демон использует только встроенные
  модули Node плюс `pg-boss` — это чистый node, конфликты вашего проекта с версиями
  Node или фреймворков на демон не распространяются.
- **Локальный Postgres очереди на :5433.** Это единственное жёсткое требование,
  которое добавляет демон. Слою памяти и координации база не нужна вовсе — он
  живёт на обычных файлах и git, — поэтому машине, которая никогда не запускает
  демона, база не нужна ни для чего.

  Либо направьте `queueUrl` на сервер, который у вас уже работает, либо создайте
  песочницу `~/pg-sandbox` (embedded-postgres, PG18), которую предполагает этот
  чек-лист: каталог с инициализированным `pgdata` и двоичными файлами
  `@embedded-postgres`. Ни прав администратора, ни docker, ни установленного
  сервера Postgres здесь не нужно:

  ```powershell
  mkdir ~/pg-sandbox; cd ~/pg-sandbox
  npm init -y; npm install embedded-postgres
  node -e "import('embedded-postgres').then(async ({default:P})=>{ const pg=new P({databaseDir:'./pgdata',user:'postgres',password:'postgres',port:5433,persistent:true}); await pg.initialise() })"
  ```

  Поднять её — и в той же команде создать базу очереди демона — стартером,
  который лежит рядом с этим файлом:

  ```powershell
  cd <SMA_HOME>
  node supervisor/pg-sandbox-windows.mjs start          # start | stop | status
  ```

  > **Пользуйтесь стартером, а не собственным `start.mjs` песочницы.** На эталонной
  > машине `node start.mjs` не вернул управление, был снят по таймауту и оставил
  > кластер в аварийном восстановлении — он принимал TCP-соединения и не отвечал ни
  > на один запрос, что любая проверка порта показывает как «поднят». Стартер идёт
  > дорогой `pg_ctl` и ждёт **сессии, которая отвечает**, а не открытого сокета:
  > кластер, который ещё проигрывает свой журнал, называется по имени (`57P03`) и
  > дожидается. Стартер идемпотентен — на уже поднятом кластере печатает «уже
  > поднят» и выходит с кодом 0 — и создаёт базу очереди (из `queueUrl`, иначе
  > `sma_queue`), если её нет, явно в UTF-8: на Windows `initdb` по умолчанию
  > делает кластер в ANSI-кодировке, а база очереди в WIN1252 не сможет хранить
  > название задачи, написанное кириллицей.

  > **База очереди, которая уже создана в другой кодировке.** Кодировка базы
  > фиксируется при её создании; никакой `ALTER` её не меняет — значит очередь,
  > созданная до того, как стартер этому научился, так и осталась в WIN1252. Демон
  > теперь говорит об этом при старте, и есть выход:
  >
  > ```powershell
  > node supervisor/queue-utf8-migrate.mjs             # только отчёт: кодировка, что ждёт
  > # остановите демона, затем:
  > node supervisor/queue-utf8-migrate.mjs --apply
  > ```
  >
  > Команда сначала выгружает всё в JSON-файл, потом создаёт новую базу UTF-8 через
  > `template0`, переносит задачи, которые ещё ждут, и строки попыток, и меняет имена
  > местами. Старая база **переименовывается и остаётся**, её никто не удаляет —
  > удалите сами, когда убедитесь. Что НЕ переносится (история завершённых задач,
  > исходные отметки времени, задача, которую в этот момент держал работник), команда
  > печатает сама — и до, и после.
  >
  > Пока Вы её не запустили, ничего не проглатывается молча: название задачи, которое
  > такая база не может хранить, получает отказ той же фразой — база, последствие и
  > команда починки — вместо «внутренней ошибки».
- **Зависимости демона.** `pgboss-backend.mjs` подключает `pg-boss` и `pg` лениво.
  Эти пакеты не объявлены в корневом `package.json` продукта; поставьте их
  машинно-локально в `node_modules` (в git они не попадают). Совместимая версия —
  `pg-boss@11`: у v12 нет default-export, который ждёт код; у v10 нет
  `getQueueStats`.

  ```powershell
  cd <SMA_HOME>
  pnpm add pg-boss@11 pg    # либо: npm install --no-save pg-boss@11 pg
  ```

## 2. Конфигурация машины (machine-local, в git НЕ попадает)

Файл `~/.sma-daemon/config.json` создаётся при первой загрузке демона со свежим
64-символьным токеном фронта. Создать его заранее одной командой:

```powershell
cd <SMA_HOME>
node --input-type=module -e "import('./daemon/src/config.mjs').then(m=>m.loadConfig())"
```

Затем задать в нём:

- `queueUrl` = `postgres://postgres:postgres@localhost:5433/sma_queue` — выделенная
  база очереди на :5433. НИКОГДА не база `postgres` и НИКОГДА не продакшн-база.
- `bind` = `127.0.0.1` (0.0.0.0 — только явное согласие).
- `expireMs` — сколько работник может молчать, прежде чем его задачу заберут
  обратно, в миллисекундах (по умолчанию `120000`, две минуты). Одна настройка —
  одни часы: это же число служит и арендой самой очереди, и подметанием, которое
  возвращает задачу молчащего работника, поэтому увеличение двигает оба. Всё, что
  не является положительным числом, игнорируется — остаётся значение по умолчанию.
- `workers` — для этого ПК один честный локальный работник:

  ```json
  { "id": "local-1", "lane": "prod", "provider": "claude",
    "account": { "name": "local-1", "configDir": "C:\\Users\\<you>\\.sma-accounts\\local-1",
                 "oauthTokenEnv": "SMA_LOCAL_1_TOKEN", "spendLogsDir": "C:\\Users\\<you>\\.sma-accounts\\local-1\\spend" },
    "enabled": true }
  ```

- `orchestrator` — **руками не пишется.** Верхушка машины заводится сама во время загрузки
  настроек и сама же записывается в этот файл; работником она не является и задач из очереди не
  берёт. Строка про неё, вписанная в `workers`, при следующей загрузке из списка вынимается.

> **Про режим 0600.** На win32 `chmod` — задокументированный no-op; демон пытается
> его применить и молча игнорирует неудачу. Эквивалент 0600 на Windows обеспечивает
> ACL профиля пользователя: файл лежит в `~/.sma-daemon` под вашей учётной записью
> и по умолчанию читается только владельцем. Файл никогда не коммитится и никогда
> не печатается обёрткой или смоуком.

> **Про реальную учётку.** Привязка headless-аккаунта (`claude setup-token` → токен
> в переменной окружения `SMA_LOCAL_1_TOKEN`) — часть НАСТОЯЩЕГО ночного прогона, а
> не смоука. Смоук проверяет контур синтетической echo-задачей, без трат на модель.

## 3. Приёмочный прогон — смоук контура (ЭТО и есть проверка)

Сначала поднять песочницу Postgres (если ещё не запущена), затем запустить смоук:

```powershell
cd <SMA_HOME>
node supervisor/pg-sandbox-windows.mjs start --db sma_queue   # безвредно, если уже поднят
node supervisor/live-smoke-windows.mjs
```

Смоук доказывает на РЕАЛЬНОМ долговременном состоянии цепочку: очередь принимает →
работник забирает из pg-boss на :5433 → появляется квитанция (`receiptRef`) →
результат виден в `GET /api/state` с токеном. Выход 0 = зелёно. Он также проверяет
отрицательную аутентификацию: `GET /api/state` без токена → 401.

## 4. Регистрация и включение задачи — ТОЛЬКО ВЛАДЕЛЕЦ

Эти две команды в настройку выше не входят. Их запускает владелец машины вручную,
когда решит, что ночной работник должен включиться. Перед импортом заменить
`<SMA_HOME>` в `sma-daemon-windows.task.xml` на абсолютный путь клона SMA.

```powershell
# выполняет только владелец
schtasks /Create /TN SMA-Daemon /XML supervisor\sma-daemon-windows.task.xml
schtasks /Change /TN SMA-Daemon /ENABLE
```

Задача поставляется с `<Enabled>false</Enabled>`, поэтому даже случайный импорт не
запустит работника. Снять её позже: `schtasks /Delete /TN SMA-Daemon /F`.

## 5. Дальнейшее (настоящий прогон)

- **Настоящий ночной прогон size:S бэклог-задачи** запускает владелец ПОСЛЕ
  включения задачи. Тогда демон реально забирает готовую задачу из бэклога,
  разворачивает worktree, спавнит работника и проходит reverify-гейт — единственную
  дверь в «выполнено».
- **Отчёт в Telegram и экономика спенд-леджера** едут на этом настоящем прогоне, а
  не на синтетическом смоуке. Смоук намеренно дешёвый: он доказывает контур, а не
  наполняет ночную статистику.

## 6. Первый прогон из приложения

Всё выше поднимает машину. Этот раздел готовит её к прогону, в котором работа
запускается из приложения, а не из командной строки — и, что важнее, к тому, чтобы
**потом это доказать**. Утверждение простое: столько-то рабочих дней подряд в
терминале оставались только четыре вида работы, о которых договорились — замер,
хирургия истории git, снос фреймворка из проекта и запуск или отладка самого
демона. По памяти такое не доказывается, поэтому запись ведёт машина.

Делать по порядку. Шаги 1 и 5 — решения владельца машины, и записаны здесь именно
как решения, а не как настройка.

### 6.1. Журнал терминала — хук SessionStart

Одна строка на сессию терминала, дописывается в
`~/.sma-daemon/terminal-sessions.ndjson`. Добавьте это в **пользовательские**
настройки Claude Code (`~/.claude/settings.json`) — тогда журнал покрывает все
проекты машины, а не только этот чекаут. `<SMA_HOME>` заменить на абсолютный путь
клона SMA, слэши оставить прямыми:

```json
{
  "hooks": {
    "SessionStart": [
      {
        "hooks": [
          { "type": "command", "command": "node <SMA_HOME>/supervisor/terminal-journal.mjs log", "timeout": 10 }
        ]
      }
    ]
  }
}
```

Если блок `hooks` в файле уже есть — допишите запись в него. Файл настроек ваш,
ничто здесь не переписывает его за вас.

Два свойства, которые стоит знать до того, как на него положиться:

- **Он не может вам помешать.** Любой сбой — недоступный каталог, полный диск —
  проглатывается, команда выходит с кодом 0. Журнал, способный не дать сессии
  начаться, был бы хуже отсутствия журнала.
- **Он не записывает сессии самого демона.** Работник, которого спавнит демон,
  несёт в окружении `SMA_HEADLESS`, и такие сессии пропускаются. Это и есть работа,
  сделанная из приложения; считать её терминальным запуском значило бы утопить
  доказательство в том самом, что оно измеряет.

Старт сессии знает, *когда* открылся терминал, и не может знать, *зачем*. Если вы
открываете терминал намеренно ради одного из четырёх — скажите об этом: либо
выставьте `SMA_TERMINAL_REASON` в этом терминале, либо напишите причину руками:

```powershell
$env:SMA_TERMINAL_REASON = "хирургия истории: перекладываю релизную ветку"
# или, не трогая окружение:
node <SMA_HOME>/supervisor/terminal-journal.mjs log замер перед релизом
```

Сессия без пометки считается **вне списка**. Это намеренно: доказывать должен тот
запуск, который просит его извинить.

### 6.2. Кодировка очереди

Прогон ведётся на том языке, на котором вы действительно работаете, значит название
задачи обязано пережить дорогу туда и обратно. База очереди, созданная до того, как
стартер научился просить UTF-8, живёт на ANSI-кодовой странице машины и отвергнет
любое не-ASCII название. Сначала проверка, миграция — только если проверка так
сказала:

```powershell
cd <SMA_HOME>
node supervisor/queue-utf8-migrate.mjs            # только отчёт: кодировка и что в очереди ждёт
# если это не UTF8 — остановить демона, затем:
node supervisor/queue-utf8-migrate.mjs --apply
```

Старая база переименовывается и **сохраняется**, никогда не удаляется, а экспорт
пишется в файл до любого изменения. Что миграция НЕ переносит — команда печатает
сама, до и после. Подробности в §1.

### 6.3. Токены аккаунтов в окружении демона

Каждый рабочий профиль называет переменную окружения (`account.oauthTokenEnv`); сам
токен в конфиг не пишется никогда. Переменная должна быть выставлена **в том
окружении, в котором стартует демон**, до того как он кого-нибудь заспавнит —
работник, стартовавший без неё, тратит сессию на выяснение, что он не
авторизован. Если демон запускается задачей Планировщика, нести переменную обязано
окружение задачи, а не та оболочка, в которой вы сейчас печатаете.

### 6.4. Включение конвейера

Тумблер живёт на экране **«Дом системы»**, на карточке **«Конвейер»**. Включать —
там, а не правкой `~/.sma-daemon/config.json` руками. Тумблер и есть дверь: он и
пишет настройку, и докладывает обратно, что о ней говорит демон; конфиг, правленный
руками, — это настройка, которую никто не подтвердил.

Перезапущенный демон поднимается с **выключенным** конвейером, пока его не включили
(конфиг без ключа означает «выключено»), и говорит это загрузочной строкой. Если
карточка показывает «Состояние неизвестно» — работающий демон собран до появления
тумблера: перезапустите его, и строка станет честной.

### 6.5. Задача Планировщика — решение, с квитанцией

Регистрация и включение ночной задачи — это §4, и оно остаётся там же: владелец
машины делает это руками, по явному решению. Этот раздел за вас такого шага не
выполняет, и молча это не автоматизируется ничем. Как бы вы ни решили — запишите
решение («зарегистрирована <дата>» или «намеренно не регистрируется»), чтобы
приёмка докладывала факт, а не пожатие плечами.

### 6.6. Что записать до прогона и как он читается после

Две вещи записать **до** первого дня:

- **Стартовые расходы.** Открыть экран **«Расходы»** и записать число. Тогда цена
  перехода в приложение — это число, а не ощущение.
- **Свежесть бандла.** Всё, что меняло экраны приложения, должно быть пересобрано
  (`cd spa && npm run build`), а демон перезапущен — иначе прогон измеряет вчерашний
  код. Бандл демон отдаёт с диска и подхватывает пересобранный без перезапуска, но
  новые **двери** живут в его коде и до перезапуска не появятся.

После — журнал читается одной командой:

```powershell
cd <SMA_HOME>
node supervisor/terminal-journal.mjs report --since 2026-08-10
```

Она печатает каждую записанную сессию, помечает `!` те, что вне списка, считает
каждый из четырёх видов, и **последняя напечатанная строка — число запусков вне
списка**: всё утверждение одним числом, которое прочитает и скрипт. Если журнала
нет вовсе — она так и говорит и выходит с кодом 3, вместо того чтобы напечатать
удобный ноль: отсутствие записи не есть запись об отсутствии.

### 6.7. Чтобы демон возвращался сам

После перезагрузки Windows **не поднимает демон**: это не служба, а ночная задача из §4
срабатывает только в 23:30. Машина, к которой Вы обращаетесь днём — тем более из другого
места по приватной сети, — остаётся без окна до тех пор, пока кто-то не запустит его руками.

Два пути; достаточно одного.

**(а) Ярлык в автозагрузке — без прав администратора.** Подходит там, где админа нет —
а именно на такие машины этот контур и рассчитан:

```powershell
$sma = 'C:\путь\к\sma'
$su  = [Environment]::GetFolderPath('Startup')
$w   = New-Object -ComObject WScript.Shell
$s   = $w.CreateShortcut((Join-Path $su 'SMA daemon.lnk'))
$s.TargetPath       = 'powershell.exe'
$s.Arguments        = "-NoProfile -ExecutionPolicy Bypass -File `"$sma\supervisor\start-daemon-windows.ps1`""
$s.WorkingDirectory = $sma
$s.WindowStyle      = 7   # свёрнутое окно: процесс виден в панели задач и закрывается вручную
$s.Save()
```

**(б) Задача Планировщика при входе в систему** — `supervisor/sma-daemon-logon-windows.task.xml`.
Отгружается выключенной, как и ночная. Регистрация **требует консоли с правами
администратора** (проверено: без них `Register-ScheduledTask` отвечает «Access is denied»),
поэтому на машине без админа берите путь (а).

```powershell
$sma = 'C:\путь\к\sma'
$xml = (Get-Content "$sma\supervisor\sma-daemon-logon-windows.task.xml" -Raw -Encoding UTF8).Replace('<SMA_HOME>', $sma)
Register-ScheduledTask -TaskName 'SMA-Daemon-Logon' -Xml $xml -Force
Enable-ScheduledTask   -TaskName 'SMA-Daemon-Logon'
```

**Два триггера друг другу не мешают.** `start-daemon-windows.ps1` первым делом смотрит на
порт окна и, если демон уже отвечает, выходит без действий — так что ночная задача и
автозапуск при входе не устроят двух демонов на одной очереди.

**Честное ограничение: это вход в систему, а не загрузка.** Демон должен стоять в окружении
интерактивного пользователя — его PATH, его домашний каталог, учётные данные его аккаунта, —
поэтому триггер срабатывает после входа. На машине, к которой Вы обращаетесь издалека и за
которой никто не сидит, это значит: либо настроенный автоматический вход, либо один ручной
вход после перезагрузки.

Проверено холодным стартом: при выключенных Postgres и демоне ярлык поднимает **оба** —
песочница базы стартует первой, затем поднимается демон, и окно отвечает на 7777.

### 6.8. Сторож — постановка из обычного сеанса, одной командой

Пункт выше возвращает демона после перезагрузки. Демона, упавшего среди дня, возвращает
сторож (`supervisor/daemon-watch.mjs`), и у него была та же беда, только острее: его
собственная единица запуска — задача Планировщика `sma-daemon-watch-windows.task.xml` — на
машине без администратора **не ставится вовсе**. Измерено: и `schtasks /Create`, и
`Register-ScheduledTask` из обычного сеанса отвечают «Access is denied».

Путь без прав администратора теперь ставит скрипт комплекта, а не рука:

```powershell
cd <SMA_HOME>
node supervisor/install-watch-windows.mjs           # поставить и запустить сейчас
node supervisor/install-watch-windows.mjs status    # что стоит и что крутится
node supervisor/install-watch-windows.mjs remove    # убрать и остановить
```

Что он делает, по порядку, и что говорит вслух:

- **Сначала пробует задачу Планировщика** — она лучше ярлыка: переживает выход из сеанса и
  умеет перезапуск. Её отказ **называется словами** («schtasks отказал по правам: «Access is
  denied» — задача планировщика ставится только из окна с правами администратора») и только
  после этого берётся запасной путь. Постановка, которая молча уходит в обход, оставляет
  человека с уверенностью, что на машине стоит задача, которой там нет. Флаг `--no-task`
  пропускает эту попытку, если Вы уже знаете ответ.
- **Ставит ярлык автозагрузки** — `%APPDATA%\…\Startup\SMA daemon watch.lnk`, целящий в
  абсолютный путь к `node.exe` и в `supervisor/watch-loop.mjs`. Настоящую папку автозагрузки
  скрипт спрашивает у самой Windows: на перемещаемом профиле она не там, где её посчитал бы
  расчёт, а ярлык, положенный мимо, — это тишина вместо сторожа.
- **Запускает круг прямо сейчас**, отделённым процессом: сторож, умирающий вместе с окном,
  в котором его поставили, ничего не сторожит. Живым его признаёт не вызов запуска, а взятый
  **замок**; не взят за 15 секунд — это провал с названным журналом, а не «запущено».

`watch-loop.mjs` — тот самый вечный круг, и он несёт три свойства задачи Планировщика,
без которых ярлык был бы тихим понижением: задержку перед первым взглядом (`--delay`, по
умолчанию 120 секунд — сторож, посмотревший на ещё загружающуюся машину, объявит падение,
которого не было), подъём упавшего сторожа с потолком (пять быстрых падений подряд — причина,
которую шестой запуск не изменит: круг останавливается и оставляет её в журнале) и **один
сторож на машину** (замок `~/.sma-daemon/daemon-watch.lock.json`; два сторожа объявили бы одно
падение дважды и дважды позвали подъём). Журнал круга и вывод сторожа — в
`~/.sma-daemon/logs/daemon-watch-<день>.log`, и день решается на каждую строку.

**Если сторож у Вас уже был поднят руками** — старым ярлыком с циклом внутри строки, — то
постановка перепишет сам ярлык, но УЖЕ КРУТЯЩИЙСЯ старый процесс переживёт её: замка он не
брал и о нём не знает. Закройте его окно (или выйдите из системы и войдите снова) — иначе до
следующего входа на машине будет два сторожа.

Проверено живым прогоном 29.08.2026 на референс-машине без прав администратора: `schtasks`
ответил «Access is denied» и это было напечатано словами; ярлык встал в папку автозагрузки;
круг пошёл и **пережил окно, которое его ставило** (процесс жив в следующем сеансе оболочки);
запуск того же ярлыка тем же способом, каким его запускает вход в систему, поднял круг заново.

### Наблюдения, записанные на том прогоне (READ-ONLY — тогда не патчились)

1. **tickDeps без `buildArgs`** (ожидалось). `main.mjs` не передаёт `buildArgs` в
   тик, поэтому настоящая не-'built' задача не может дойти до спавна из
   продакшн composition-root. На этот смоук не влияет (дверь preflight пропускает
   спавн).
2. **`ledger` передан в тик как СТРОКА `ledgerDir`** (ожидалось). Значит
   `ledger.recordAttempt` внутри `loop.mjs` (completeTask/failTask) — молчаливый
   no-op (гард `typeof === 'function'` его пропускает). НО строку attempt-ledger
   пишет САМ pg-boss-адаптер в своём `complete()` (`ledgerDir` проброшен в
   `createPgBossQueue`), поэтому леджер ВСЁ РАВНО наполняется — через путь адаптера,
   а не тика. Итог для развёртывания: ветка леджера в тике мёртвая как проложена;
   единственная запись идёт из адаптера (что для одной записи корректно).
3. **`createDaemon().start()` не вызывает `adapter.start()`.** Возвращаемый `start()`
   поднимает только фронт и тик; соединение pg-boss не открывается. Смоук (и
   настоящее развёртывание) должен стартовать адаптер сам.
4. **`pgboss-backend.mjs start()` ссылается на dead-letter очередь `sma.task.dead`,
   но не создаёт её.** Под pg-boss v11 `createQueue(lane, {deadLetter})` валидирует
   цель и падает с «Queue sma.task.dead does not exist» → свежий бут крашится.
   Развёртывание (или сам backend) должно создать dead-letter очередь до
   lane-очередей. На том прогоне её провиженила обвязка.
5. **`pg-boss` и `pg` не объявлены в корневом `package.json` продукта**, хотя
   `pgboss-backend.mjs` подключает их лениво. Ставятся машинно-локально (в git не
   попадают). Совместимая версия — `pg-boss@11`: у v12 нет default-export, который
   ждёт `const { default: PgBoss } = await import('pg-boss')`; у v10 нет
   `getQueueStats`; у v11 нет `touch` (но `touch` в этот контур не входит — дверь
   preflight не спавнит и не стримит). Развёртыванию стоит объявить рантайм-зависимости
   и закрепить совместимый мажор pg-boss.
